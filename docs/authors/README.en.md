# Writing plugins for chat platforms: making your package work in QQ

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page is for third-party authors who want to add features to Miyu in QQ. You write an ordinary Miyu package (an extension, skills or scripts all work). Once it is installed, the AI can use it in QQ private chats and QQ groups too.

This page only covers what is different in QQ compared with the terminal UI and the web UI. For how to write a package and its manifest, and how an extension speaks the protocol, see the core repository's author guide: [Writing a Miyu package](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/packages.md). The parameters, answers and error codes of every method are in the core's [protocol reference](https://github.com/miyu-agent/miyu/blob/main/docs/en/reference/README.md) (the methods for venue sessions are in [`venues.md`](https://github.com/miyu-agent/miyu/blob/main/docs/en/reference/venues.md)). How to call the methods of chat platforms and how to plug into its hook points are described in detail in this repository's [`docs/blueprint/extending.md`](../blueprint/extending.md) (in Chinese).

Working examples you can follow are the memes package [`memes`](https://github.com/miyu-agent/miyu-memes) (tools, injected hints, sending pictures) and the render package [`render`](https://github.com/miyu-agent/miyu-render) (a method that chat platforms call).

## 1. Things to know first

Before you write a plugin, you need to know the following:

1. **A QQ conversation is a session too.** Each group has its own session, and so does each private chat; these sessions are called "venue sessions". In a venue session the AI talks and calls tools just as it does in the terminal UI. The only difference is that the people on the other side are on QQ, and chat platforms send the AI's replies back to QQ.
2. **Venue sessions belong to the system account**, not to the admin. Chat platforms create and drive venue sessions, and the admin never sees a tool confirmation prompt for them in the terminal UI, so nobody can confirm a tool call in a venue session.
3. **Who can talk to the AI**:
   - Private chats: only the terminal admin and whitelisted members (`im.whitelist`). The AI replies to every message in a private chat.
   - Groups: only groups on the whitelist (the venue cards on the admin page), and "Other groups" is off by default. The AI listens to every message in a group, and chat platforms decide whether it replies (an @ mention of the AI, a quote of the AI's message, a trigger word, the judge's score).
4. **Whether your tool is available in a venue session depends on the `venues` you write when you register it.** Chat platforms do not pick tools for you; the core puts each tool into the sessions that its `venues` name.

## 2. Making a tool show up in QQ

When your extension registers tools with `provide`, it uses `venues` to say which kinds of session get each tool (see the core author guide, ["Writing an extension": registering tools](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/extensions.md#registering-tools-provide)):

| Value in `venues` | The tool shows up in |
|---|---|
| `local` | The admin's own sessions in the terminal UI and the web UI |
| `private` | QQ private chats |
| `group` | QQ groups |

```json
{"name": "meme_send", "description": "Send a sticker as a message of its own.",
 "input_schema": {"type": "object", "properties": {"id": {"type": "string"}}, "required": ["id"]},
 "access": "read", "venues": ["local", "private", "group"]}
```

**Rules for access categories (`access`) in venue sessions.** Because nobody can confirm anything in a venue session:

- `read` and `write` run as usual. When read-only is on, the core blocks `write`.
- `network` and `outbound` need a person to confirm, so they are always refused in venue sessions. Do not register a tool that is meant for groups with them.
- `venue` is for actions that leave a mark on the platform (recall a message, mute, poke). Such tools run directly in venue sessions without asking anyone; in local sessions they are judged by the rules for `outbound` (they run directly when permissions are fully open, and ask a person at the workspace level).
- "This turn's reply" does not count as sending something out. The memes package's `meme_send` is registered as `read`, because the sticker it sends is only part of the AI's reply this turn, and chat platforms send it together with the reply.

**Who is talking to the AI.** `tool.call` carries `by` and `owner` (see the core author guide, ["Writing an extension": being called](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/extensions.md#being-called-toolcall)):

- `by` is the sender of the message the AI is answering at that moment, for example `{"kind": "external", "venue": "qq:group:123", "id": "qq:456", "role": "manager"}`. In a group, whenever a new message arrives and the AI sees it, `by` changes to the sender of that message.
- `owner` says whether the core recognizes that person as the owner.
- For tools registered as `venue`, **the core does not keep people out for you**. Who may use the tool (only the owner? only the group's admins?) is for you to decide and enforce from `by.role` and `owner`; when you refuse, reply with a tool result that explains why, and set `error` to true.

**Which group it is.** `tool.call` gives you a session id. To find out which group it is and which bot account it came through, call the `chat.venue` method of chat platforms (see section 7).

## 3. Adding hints to the conversation

An extension can add a hint to every turn of the conversation. If the extension declares `context.inject` (see the core author guide, ["Writing an extension": more abilities](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/extensions.md#more-abilities)), the core asks you once at the start of every turn by calling `user.append {"session", "venue", "text"?}`. `venue` is `local`, `private` or `group`, and you can use it to decide whether to add a hint in QQ and what it says. The answer has the form `{"content": [{"kind", "text"}]}`, with at most 3 blocks; they go after the message that started the turn, are written to the log, and are replayed unchanged afterwards.

- If you do not answer within 300 milliseconds, the turn counts as having no content from you.
- You handle wrapping and escaping yourself: `text` goes into the context as is.
- Only state what something is, do not give commands, and write short English sentences. The memes package's hint is `<meme-hint>This reply comes with a sticker.</meme-hint>`, and it is given with a certain probability.
- Text that is sent on every turn costs tokens in every group on every turn, so keep it small.

## 4. Sending pictures

There are two ways to send pictures:

1. **Include `sent` in the tool result** (this is what the memes package does). First upload the picture with `blob.put`, then add a `sent` field to the tool's answer:

   ```json
   {"blocks": [{"type": "text", "text": "Sent."}],
    "sent": [{"blob": "<from blob.put>", "media_type": "image/gif", "width": 240, "height": 240, "alt": "A cat waving.", "sticker": true}]}
   ```

   You can send at most 4 pictures each time. `sent` is not passed to the model (the AI only sees `blocks`); chat platforms use it to send the pictures to QQ. Each picture becomes one image segment, and together with the AI's words it is put into the outbound queue in the order of the AI's calls. When `sticker` is true, the picture is sent as a real QQ sticker (the OneBot image segment carries `sub_type=1`). If a picture cannot be sent because of a mute or because it expired in the queue, chat platforms record an `unshown` fact for the AI, so the AI knows the picture was not sent. `path` is not accepted even if you write it; you must use `blob.put`.

2. **The AI calls the core's `show`** to show someone a file from the workspace. Images are sent as pictures, and other files are uploaded as QQ files. Your tool only needs to write the file into the workspace and return its path, and the AI decides whether to send it (the render package's `render_image` works this way).

## 5. Groups versus private chats

The table below compares private chats and groups.

| | Private chat | Group |
|---|---|---|
| Who can talk | The terminal admin, whitelisted members | All members of a whitelisted group |
| Which messages the AI answers | Every message | Messages that chat platforms have judged (@, quote, trigger word, judge score) |
| `by` | The other person | The sender of the message the AI is answering at that moment; it changes |
| Whether your tool is available | Depends on whether `venues` includes `private` | Depends on whether `venues` includes `group` |
| The session belongs to | The system account | The system account |

Groups have many people and many strangers. A tool that changes anything must keep people out based on `by` and `owner`; do not assume that "the AI asked me to do it" means the owner asked.

## 6. The system account and permissions

Venue sessions belong to the system account, and the following points concern its permissions:

- **Workspace.** A venue session can only access its own workspace (the core's file tools check the real location). Your extension process, however, is **not under this limit**: it is your program, and the core cannot control what it reads or writes. So do not open a path from `tool.call` directly. Judge it by its real location (after resolving links) and require it to be inside `cwd` (the working directory of the turn). When you write a file, write a newly created temporary file first and then rename it, so that you never follow a link planted beforehand and write outside. The render package's `render_image` is a model you can follow (`src/tools/render_image.rs`, `src/tools/saved.rs`).
- **Untrusted text.** People in a group can write any text, and that includes nicknames and group cards. If you put such text into a prompt for the model, escape it and wrap it, so that nobody can forge a line that looks like "the system says".
- **`blob`.** Pictures you upload with `blob.put` are stored under the admin. Chat platforms can read the pictures you hand over in a tool result's `sent`, and the ones you hand to them in a method's answer (the core is adding this rule).
- **Calls the core refuses.** When an extension calls methods that are meant only for local users, such as `extension.*` and `package.install`, the core refuses them (`local_only`).

## 7. Working with chat platforms

Your extension can call chat platforms, and chat platforms can call your extension. When you call chat platforms, you use their name on the bus, `chat`: `bus.call {"name": "chat", "method": "venue", "params"}` (`method` is the part after `chat.`, not the package id of chat platforms). Chat platforms call you over the bus too, through the name `chat.hook` that you plug into (see the core author guide, ["Writing an extension": more abilities](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/extensions.md#more-abilities)). For this, the manifest must declare `packages.call`, and a person must approve it.

**You call chat platforms** (details in [`extending.md` section 1](../blueprint/extending.md#一调接入通讯平台-的方法)):

- Hook points and methods are all named `chat.*`. The parameters that chat platforms hand you and the answer of `chat.venue` all carry `platform` (only `qq` for now). When you call a method you may pass `platform`; if you leave it out it counts as `qq`, and any other platform is refused with the error `bad_params`.
- `chat.send {user | group, text}`: send a message in the AI's name. The message goes through the outbound chain, and the receiving session records a fact, so the AI knows that it started the conversation.
- `chat.action {action, params?, bot?}`: run a OneBot action for you (kick someone, list group members, fetch an image…), and hand NapCat's answer back to you unchanged. The AI does not know that messages sent this way are its own words.
- `chat.venue {session}`: look up which group and which bot account a session id belongs to.

**Chat platforms call you**:

- **Hook points** (details in [`extending.md` section 2](../blueprint/extending.md#二插进接入通讯平台-里面)): declare `plugs = ["chat.hook"]` in the manifest, export and register the agreed methods under that name, and they are hooked up once your package is installed and running. The hook points are: `chat.hook.event` (QQ notices and requests, handed to you as is), `chat.hook.inbound` (asked before a group message is judged: handle as usual, only record, reply directly), `chat.hook.outbound` (asked before the AI's words go out: replace, do not send, keep as is), `chat.hook.score` (asked after the judge has scored, whether to add or subtract points). `chat.hook.event` does not wait for your answer; the other three wait at most 1.5 seconds and treat no answer as no opinion.
- **Agreed services**: these are package ids and method names that chat platforms know, and chat platforms use them once they are installed. There is one now: `render`'s `markdown {markdown}` → `{pages: [{blob, width, height}]}`. Chat platforms hand long replies over the threshold to it to be rendered as pictures (the `Long text` field on each venue card). If you write a package with the same id and the same method, you replace how the rendering is done; if the call fails or times out (15 seconds), chat platforms split the text into several messages instead.

## 8. Trying it in QQ

These are the steps to test your package in QQ:

1. Get chat platforms running first: install NapCat and log in the bot account, run `miyu im start`, then run `miyu im web` to open the admin page, put the token into NapCat, and set up the terminal admin and whitelisted members on the admin page. Run `miyu im status` to see whether it is connected.
2. Install your package: run `miyu pkg install ./your-package`, answer "turn it on" and approve the capabilities (see the core author guide, ["Install, try, check"](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/packages.md#install-try-check)). The tools in venue sessions follow package changes: sessions that are already open get the new tools on their next turn.
3. From the terminal admin's QQ account, send a private message to the bot account and ask the AI to call your tool. To test in a group, add a group to the whitelist on the admin page, turn it on, and then @ the AI.
4. See what happened:
   - `miyu im logs -f`: the run log of chat platforms (decisions, queueing, whether messages were sent, whether hook points answered).
   - `stderr` in `MIYU_LOG_DIR`, the log directory the core gives your program: your program's standard error output (read every directory the core provides from its environment variable; do not build paths from `MIYU_HOME` yourself).
   - `miyu im venue show qq:group:<group number>`: the value of every setting of that group and where it comes from.
5. If the preset has your package turned off, venue sessions do not have your tools. In that case, check which persona and preset the venue card on the admin page uses.

## 9. Manifest

Here is an example manifest:

```toml
[package]
protocol = [1, 1]
name = { en = "Hello", zh = "你好" }

[command]
name = "hello"
program = "hello"
about = { en = "Hello package", zh = "你好" }

[process]
args = ["serve"]
start = "always"
capabilities = ["tools", "context.inject", "packages.call"]   # list only the ones you use

# Only packages that plug into the hook points of chat platforms need this:
[depends]
packages = ["im"]

[export]
plugs = ["chat.hook"]
methods = ["chat.hook.inbound"]
```
