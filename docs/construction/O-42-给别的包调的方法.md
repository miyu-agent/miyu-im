## 施工单 O-42：扩展口（上）：给别的包调的方法

状态：已合（02b9179，2026-10-17）。2026-10-17 项目主人定：接入QQ 的新功能以后能做成单独的包装（例如 `miyu pkg install miyu-onebot-qq-admin`），扩展口分三步做：给别的包调的方法（这一步）、包之间的依赖（核心做）、插进桥里面（进站、出站、QQ 事件、判断打分，O-43）。

### 目的

现在别的包装上了也碰不到 QQ：接入QQ 的清单没有 `[export]`，`packages.call` 调不到它（核心 X-18：只调得到对方 `[export]` 里的）。这一步开两个口：

1. `qq.action`：替别的包调一个 OneBot 动作（踢人、禁言、发消息、查群成员……），原样交回 NapCat 的回答。
2. `qq.venue`：一个会话是哪个群、哪个私聊。别的包提供的工具被调时，核心交来的是会话编号（`tool.call` 的 `session`）；场所会话归系统账号，`venue.sessions` 只给系统账号的连接，别的包问不到，由桥答。

### 蓝图改哪几节

- 新的一页 `docs/blueprint/extending.md`「给接入QQ 写扩展包」：写给扩展包的作者，只写对外的约定，链到 `onebot.md`。这一步写「调接入QQ 的方法」一节：清单怎么写（`[process] capabilities` 加 `packages.call`，人批过；`[depends] packages = ["onebot"]` 等核心做完再写进去）、两个方法的参数、回答、拒绝。
- `onebot.md` 第一条加一段「给别的包调的方法」（O-42）：
  1. 清单 `[export] methods = ["qq.action", "qq.venue"]`；照旧经 `package.methods` 登记（和 `status`、`connection.token` 一起）。后台页的两个方法不进 `[export]`，别的包调不到。
  2. `qq.action {"action", "params"?, "bot"?}`：`action` 是 OneBot 动作名（小写字母、数字、`_`，最多 64 个），`params` 是对象，不写是 `{}`。`bot` 是机器人的号，不写照连着的号里最小的那一个（同后台页的 `status`）。照桥自己调动作的路发、等 `call_timeout_seconds`（`bridge.json`），回 NapCat 的回答 `{"status", "retcode", "data", "message"?, "wording"?}` 原样。没连着 NapCat 回错 `not_connected`；等不到 `unanswered`；写错 `bad_params`。
  3. 不挑动作：调得到 `qq.action` 的包是人批过 `packages.call` 的，能做的和 NapCat 能做的一样（2026-10-17 照推荐定，见「要拍板的」第 1 条）。运行日志一行 `INFO export action from=<包> action=<名字> retcode=…`，不记参数、不记回答。
  4. 她自己说的话不走这里：`qq.action` 发出去的消息不过出站链、不进出站队列、不记 `venue.delivered`，她不知道这句话是她说的。要让她知道的，随 O-43 的出站挂接点。
  5. `qq.venue {"session"}`：回 `{"venue": "qq:group:123" | "qq:private:456" | null}`，照桥这一刻认得的场所会话（群的订阅表、私聊找过的）；认不得的 `null`。
- `onebot.md`「在哪」：加 `core/exports.rs`（或 `core/methods/exports.rs`）一行。

### 要拍板的（技术的照推荐定，留痕）

1. `qq.action` 不设白名单。推荐：不设。人批 `packages.call` 的时候就是在批「这个包能让 QQ 做事」；列白名单要跟着 NapCat 的扩展动作改，挡不住真想做事的包，只增加维护。没选：只开一张动作表。
2. 方法名带 `qq.` 前缀。推荐：带。和挂接点（O-43 的 `qq.inbound` 这类，由别的包导出、桥来调）放在同一个名字空间，作者一眼看出是接入QQ 的约定。
3. `qq.venue` 只认桥认得的会话。推荐：照桥手里的表答，不去问核心。桥手里没有的（还没来过一条消息的群）回 `null`；别的包拿到的 `tool.call` 都发生在场所会话里，那个会话桥一定认得。

### 不做什么

- 不做「她说一句」的口子（要过出站链、记 `venue.delivered`）：O-43 的出站挂接点一起考虑。
- 不做包之间的依赖：核心做（2026-10-17 已经发给核心的会话，形状照 pacman：`[depends] packages`）。
- 不改后台页。

### 验收

- 测试当别的包：真核心、真桥、一个只声明 `packages.call` 的测试扩展（核心测试里有现成的写法），经 `package.call` 调 `qq.action {"action": "get_group_member_list", "params": {"group_id": 1}}`，假 NapCat 收到同样的动作、回什么交回什么；`set_group_ban` 这类写的动作同样转过去。
- 没连着 NapCat：`not_connected`；NapCat 不回：`unanswered`；`action` 写错、`params` 不是对象：`bad_params`；两个号连着、`bot` 写了的发到那一个，没写的发到小的那一个。
- `qq.venue`：群、私聊的会话照回，认不得的 `null`。
- 后台页的 `status` 别的包调不到（`not_exported`），人照旧调得到。
- 运行日志不带参数、回答。
- 变异 15 个左右；`cargo xtask check` 全过，三平台 CI 绿。

### 风险

- 别的包用 `qq.action` 发消息，她不知道自己说过：写进 `extending.md`，作者要她知道的等 O-43。
- `packages.call` 要人批：没批的包调不到，核心回 `needs_approval`，作者照核心的说法提示人去批。
