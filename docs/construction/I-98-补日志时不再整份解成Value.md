## 施工单 I-98：补日志时不再整份解成 Value

状态：做完了（2026-11-02；核心性能线 4c 查出来的）。

### 目的

部署上的 miyu-im 一个进程 PSS 527 MB（同一个数据根里别的包几 MB）。4c 11-02 拿主人数据根的演练副本复现、用 heaptrack 按分配点拆：

- 起来订阅群会话从 seq 0 补日志时，补来的事件推送在 `Core::call_as` 等 `subscribe` 回应的那一会儿全解成 `serde_json::Value` 堆进留着的里面，整份日志同时活着；一条约是原文的 7 倍。最大的群 3.77 万条（日志 22.7 MB）峰值 187 MB，其中约 183 MB 是这些 `Value`。
- glibc 一次冲高不还页：revive 完匿名内存 217 MB，空闲时活着的堆只有 7.4 MB；手动 `malloc_trim` 能降到约 70 MB。
- 投影本身空闲时约 5.6 MB（每条事件约 140 字节），不是大头。

### 图纸改哪几节

- 蓝图 `onebot.md` 文件表：`core.rs` 那一行补「事件推送留原文」，多 `program.rs` 一行。

### 怎么走

1. 读的一头碰到事件推送（`method` 是 `event`、没有编号）只看一眼方法、会话（借用的轻量反序列化，别的格照 JSON 走过去、不分配），原文留成 `Box<str>`；回应、别的推送、核心发来的请求照旧当场解成 `Value`（`core/incoming.rs`）。
2. 留着的推送存原文；`take_events`、`take_events_of` 交回一个迭代器，取一条解一条，同时活着的 `Value` 只有手上那一条。`next` 取到原文的当场解。
3. 起运行时以前调一次 `miyu_client::heap::tune()`（核心那一套）；`revive` 补完以后在 `spawn_blocking` 里 `trim()` 一次。

### 不做什么

- 起来不从 seq 0 补、只补最近一段，投影剪老的、`Turn.by` 存序号：动行为（续聊、冷静、补发的窗口要逐个看），另排一步（I-99），连同上面剩的几样小头。

### 量出来的数

4c 11-02 照同一套复现量（主人数据根演练副本重拷，删密钥、去掉模型、不 resume，断网命名空间；核心 f69013f2，release 带调试信息；补完日志、日志静下来再等 20 秒读 smaps；改前、改后交替各三次）：

| | 改前（I-97） | 改后（I-98） |
|---|---|---|
| 补完以后 PSS | 227–232 MB | 24–27 MB |
| 补完以后匿名内存 | 217–222 MB | 14–15 MB |
| 峰值 RSS | 231–236 MB | 47–48 MB |
| 堆峰值（heaptrack） | 187.3 MB | 35.6 MB |
| 空闲时活着的堆 | 7.44 MB | 7.44 MB |

改后峰值里还剩：整份日志原文在 `subscribe` 回应到以前留着（26.5 MB），两份 `VecDeque` 缓冲（各 2.6 MB），每条一份的会话编号（1.4 MB）。都只抬峰值、常驻影响很小，随 I-99（边收边进投影、原地取、会话编号不重复存、`Turn.by` 存序号）。

### 验收

- `src/core/incoming/tests.rs`：事件推送留原文、认得出会话（带转义的也认）、取的时候解得回原样；有编号的、别的方法、回应照旧当场解；不是 JSON 的报错；取出来的照先后。
- 原有的跟核心那一头、群、私聊、补日志的测试全过（留着的推送照先后、一条都不丢）。
- 本机门禁、三台 CI 全绿。
