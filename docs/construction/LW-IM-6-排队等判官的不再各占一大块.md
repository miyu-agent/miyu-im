## 施工单 LW-IM-6：排队等判官的消息不再各带着一整段

状态：做完了（2026-11-23）。

### 为什么

每条要问判官的群消息起一个任务（`judges.rs`），任务里是整个「问一次」（`ask.rs`）：排队、`venue.records`、拼请求、几次
`model.call` 之间的状态，约 2 KB，交出去的那一刻就整块分配，排着等名额（`judge_concurrency` 4 个、最多等 15 秒）的每一条都带着
它。2026-11-23 用 heaptrack 量过：5 个群一阵灌 5000 条时，峰值里 11.8 MB 是这些排着的任务。glibc 把峰值留在分配区里，安静以后
也还不干净。

### 怎么改

1. `ask.rs`：`ask` 不再是一整个 `async fn`。交进来的几样（`Asking`、调用口、判官的字、人格）先一起放进堆上的一块（约 0.6 KB），
   任务里只有它的指针、名额和排队的时限；占到名额以后的那一段（`asked`）另放在堆上，这时才分配。
2. `judges.rs`：问判断打分挂接点的那一段同样另放在堆上，排着的任务不带着它。
3. 先后、15 秒的时限、耗时都照原来从交给判官那一刻算：任务还是交出去就起，排队照旧是 tokio 的信号量（先来先得），只是排着的
   那一段变小了。判断、记录、交回的样子一样都没变。

施工方案里写的是「路由里排小结构、名额空出来才起任务」。动手时发现照原来「交出去就起任务、任务里排队」只把排着的那一段挪小，
先后和时限的语义原样不变，改动也小；排着的每一条从约 2.2 KB 降到约 0.6 KB 加一个小任务，占大头的已经拿掉，就照这个做。参数
（`Judge`、`Chatty`）没有换成 `Arc`：`Asking` 一共 456 字节，测试里直接改它的格子，换了要改测试的写法，收益不到 0.3 KB 一条。

图纸：`docs/blueprint/onebot.md` 第一条「在哪」`ask.rs` 一行补一句。

### 测试

- `ask/tests.rs` 新的 `a_queued_ask_does_not_carry_the_asking_part`：交出去、还没占到名额的那个任务，比占到以后的那一段小一半以上
  （改前两段是一个，这一条红）。
- 原有的测试一条没改，门禁全过。

### 量（沙箱，5 个群各 1000 条；改前改后各三遍交替着量，PSS，kB）

| | 改前 | 改后 |
|---|---|---|
| 每秒约 250 条：灌的时候最高 | 35624 / 35747 / 35937 | 29801 / 29753 / 29816 |
| 每秒约 250 条：安静 30 秒以后 | 30098 / 30138 / 30757 | 27207 / 27141 / 27216 |
| 同上，线程分配区驻留（gdb 走的） | 15056 / 15052 / 15664 | 12068 / 12072 / 12120 |
| 每秒约 900 条：灌的时候最高 | 30156 / 30166 / 31130 | 26663 / 27563 / 28229 |
| 每秒约 900 条：安静 30 秒以后 | 24109 / 23870 / 24769 | 24119 / 24735 / 25281 |

- heaptrack（每秒约 900 条，各一遍）：堆的峰值 11.95 → 9.59 MB，排着的那一处 6.12 → 2.73 MB。
- 每秒 900 条时安静以后的数在波动以内。那时排满 15 秒的多半照「判不了」算掉（问到模型的约 1600 次，每秒 250 条时约 2700 次），排着的那一阵短，这是推断。这一组量的时候本机负载有一段到了 23–28（别的会话在编译）。
- 处理完的用时两边一样（每秒 250 条 20.8–21.5 秒，每秒 900 条 7.9–10.0 秒）。
