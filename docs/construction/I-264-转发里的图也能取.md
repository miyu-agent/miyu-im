## 施工单 I-264：`qq_fetch_media` 的说明写明合并转发里的也能取

状态：做完了（2026-11-20），等合并。

### 起因

2026-11-20 项目主人报：引用合并转发问 AI，AI 说拿不到里面的图。主人本机那个群会话的记录：

- 至少 10 次回过「转发里的图我看不到」这一类的话，最近一次在 11-20 12:57。
- 96 个合并转发，`qq_fetch_media` 一次也没往转发上调过。同一个会话里普通的图、文件调过 38 次，几乎都取到了。
- 推理里一律写「The forward image wasn't described to me」这一类，当成看不到。
- 压缩摘要从 11-14 起把「看不到转发里的图、照实说了」当成好做法记下来，一路带到 11-20。

转发里的图在模型看到的记录里写成 `[image #1]`，用 `qq_fetch_media` 填外面那条的 `msg`、`index` 填 1 就能取（I-75 起就能取）。说明只有一句「Fetch an image, video or file from a message.」，没提转发，模型拿不出依据推翻自己的印象。

### 改了什么

- `im/data/onebot/tools/qq_fetch_media.json`：说明改成「Fetch an image, video or file from a message or a forward in it.」，`index` 改成「The #n shown. Default 1.」。
- 工具面预算 4840 → 4870 字节（`crates/miyu-im-app/tests/budget.rs`；项目主人 11-20 定）：说明合计 4834 → 4867。
- 登记簿、图纸「平台工具（二）」第 1 条照改；下一版发版说明加一条。

问过、没做的两件：引用转发时像引用普通图片一样自动取图（项目主人定不做）；压缩模板把「做不到」当好做法记下来的问题（项目主人定先不管）。

### 给模型看的字

开发网关的 `deepseek-v4.1-flash` 量，工具面照「带工具减不带」：驱动的二十二件一起时 `qq_fetch_media` 的边际 90 → 100，二十二件合计 1824 → 1834。tools 数组改一次，是一次计划内的冷启动，之后照旧字节恒定。

### 怎么验

- 预算门禁（`the_bridge_tool_face_stays_within_its_budget`）、登记簿指纹门禁过；门禁八项；三台 CI。
- 真模型实测：沙箱用和 im 同钉的核心（f9028fcea）、假 NapCat，模型是开发网关的 `deepseek-v4.1-flash`，数据根每趟新建。剧本分两轮：第一轮引用一个合并转发 @ 她，转发里的图故意取不下来；第二轮再来一个合并转发，图取得下来，引用它叫她锐评。

  | 说明 | 第二轮取到图 | 回话说中图里的内容 |
  |---|---|---|
  | 旧 | 4/4 | 3/4 |
  | 先试的长一版 | 4/4 | 4/4 |
  | 合进去的这一版 | 2/2 | 2/2 |

  干净的上下文里，旧说明也会去取，主人那边是压缩摘要把错的印象带了下来。新说明给出依据，效果在主人本机上等真机核对。
