## 施工单 LW-IM-8：发行程序照执行的先后排函数

状态：本机和测试机上做完了（2026-11-23）；发版的流程怎么接另定（见最后一节）。

### 为什么

`miyu-im` 的代码段 13 MB，空闲时常驻 8–9 MB，灌过消息 11 MB；真正执行过的函数只有 2.7–4.3 MB（2026-11-23 在 QEMU 里录过）。
没排过的程序里，执行过的函数散在整个代码段，每碰一个就带进相邻的一片页。核心 LW-1 照执行的先后排以后，常驻的代码约等于执行过
的那些。

### 怎么改

1. `crates/miyu-im-app/build.rs`：认 `MIYU_IM_LINK_ORDER`（清单的绝对路径），给 `miyu-im` 加 lld 的 `--symbol-ordering-file`；
   没设的什么都不加；别的系统上设了的构建失败；清单变了重链。
2. `cargo xtask order`（`xtask/src/order.rs`，Linux x86_64，要 `qemu-x86_64`、`nm`）：
   1. 清单写成空的，照发行那样编 release 的程序、拷一份另放（录的是它：编测试时依赖多开了几样功能，函数的符号名对不上发行的
      程序，第一版就撞上了：4853 个里只找到 1179 个），再编 release 的集成测试。
   2. 五段，一段一组集成测试（群聊；取图和文件；页面；Telegram；管理和看一眼），带着 `MIYU_IM_TRACE`。测试程序旁边的
      `miyu-im` 换成一个小脚本（`tests/support/traced.rs`）：`serve` 经 QEMU 用户态模拟器带 `-d page,in_asm` 跑上面拷的那一份，
      别的子命令照常。只有桥在模拟器里，测试程序、进程内的真核心、假 NapCat、假 Bot API、页面的请求都原生跑，所以清单里只有
      `miyu-im` 自己的函数。`page` 那张表的第一行是程序装在哪，地址照它换回程序里的。
   3. 日志照 `nm` 换成函数（`order/listing.rs`）：头一段照第一次执行的先后，后面每段只把新见到的接在后面，不常走的路径整段排在
      最后、不插进常走的中间。每段换完删日志。
   4. 写好清单再编一遍程序：只重链 `miyu-im`。
   5. 核对（`order/verify.rs`，照核心的九成线）：清单里的名字九成以上要在这一份程序里找得到，找到的九成以上（按字节）落在代码段
      开头 1.25 倍以内。录不出、一段一份日志都没有、模拟器没装、对不上、排不上都报错退出，不交没排的程序当排过的。段里个别测试没
      过只打一句：模拟器里慢，影响的只是录到多少。
3. 录的剧本用的是现成的集成测试，等字、等效果都是照事件等，不照时间猜，模拟器里慢也照样走完（这一次五段 165 个测试全过）。

图纸：`docs/blueprint/onebot.md` 第一条「在哪」多 `xtask/src/order.rs` 一行。

### 测试

- `order/listing/tests.rs`：符号表只认带大小的代码符号；装载起点照布局表；指令行的地址；照先后去重、代码段以外的不算、第二份接着收。
- `order/verify/tests.rs`：排在开头的过、散着的报错、空清单和找不到的报错、一半名字对不上的报错、同名的局部函数一起算。
- 门禁全过，原有的测试一条没改。

### 量（沙箱；同一份代码排过和没排过的程序，各三遍交替着量，PSS，kB）

| 状态 | 没排 | 排过 | 其中常驻的代码 |
|---|---|---|---|
| 没配平台，空闲 30 秒 | 11873 / 12057 / 11757 | 7003 / 7004 / 7077 | 8.0–8.4 → 3.4 MB |
| 接上假 NapCat，空闲 30 秒 | 12364 / 12568 / 12366 | 7402 / 7436 / 7371 | 8.6–8.8 → 3.6–3.7 MB |
| 5 个群各 200 条，安静 30 秒 | 18786 / 18972 / 18775 | 14383 / 14357 / 14300 | 11.0–11.1 → 6.6 MB |

- 清单 4846 个函数、7.1 MB，九成线核对是 100% 排在开头；处理消息的用时一样（4.1–4.3 秒）。
- 灌过消息以后常驻的代码（6.6 MB）比那一阵执行过的（约 4.3 MB）多：清单照五段测试录，覆盖得比这一种用法宽，同一段里常走和
  不常走的挨着，带进来一部分。
- 发版多花多久（另一台测试机，依赖都编好了以后）：照发行那样编程序 114 秒；`cargo xtask order` 一共 696 秒，其中五段测试在
  模拟器里一共跑了 192 秒，其余是多编一遍 release 的集成测试和两次重链（没有分开计时）。

### 发版怎么接（另定）

发版用的是 `miyu-agent/packages` 的 `pack.yml`，im 这边只交一段构建脚本（`.github/workflows/release.yml` 的 `build:`）。Linux x86_64 那
一份要：装 `qemu-user`（`binutils` 的 `nm` 镜像里有），构建那一句换成 `cargo xtask order`；macOS、Windows 照旧。`cargo xtask order`
失败时这一步失败，不发。这一步这次没有改，等定了再动。
